# Phases: protocol for autonomous, self-correcting research

This folder turns the Gimbal project into ten executable phases. A human starts a phase by telling an
AI agent "execute phase NN". The agent then works autonomously until the phase's exit gate passes,
the phase is shown to be impossible as specified, or an escalation condition (Section 9) is met.

The protocol has two properties that matter more than any single phase:

* **Self-correcting.** A failed gate is not a stopping point. The agent diagnoses the failure,
  researches it (including searching the internet and reading primary sources), changes the
  mathematics, theory or code, re-verifies and re-runs the gate, and repeats.
* **Adaptive.** Phases depend on each other through named artifacts. When a piece of mathematics,
  theory or code is replaced, every phase and document that depended on it is marked stale and
  rewritten, and the theory paper is updated, before any downstream work continues.

## 1. Before any phase

1. Read this file, `AGENTS.md`, `phases/STATUS.md`, `research/state.md` and the phase file.
2. Clone the research skills and follow them; they are part of this protocol:
   `git clone --depth 1 https://github.com/tasmaikeni13/skills /tmp/skills`

   | Skill | Use it for |
   |---|---|
   | `literature-frontier` | any literature search, novelty check, related work |
   | `theory-research` | statements, proofs, counterexamples, Lean, proof audits |
   | `mechanism-transfer` | importing a mechanism from another field |
   | `ml-research` | hypotheses, baselines, controlled experiments, claims |
   | `experimental-research` | Monte Carlo design, measurement models, uncertainty |

3. Reproduce the entry state: build the Lean project (`cd formal && lake build`), run the tests
   (`pytest -q`), and re-run the cheapest experiment the phase depends on. If the entry state does not
   reproduce, that is the first failure to fix (Section 4); do not build on an unreproduced state.
4. Set the phase to `in_progress` in `phases/STATUS.md` with the date and the commit hash.

## 2. Ground rules

* **Never fabricate.** No invented numbers, runs, citations, or proofs. A run that did not finish is
  reported as not finished. `sorry`, `admit` or new axioms in Lean count as unproved.
* **Keep failures.** Failed runs, killed hypotheses and refuted lemmas stay in the ledgers with their
  mechanism. Deleting evidence that hurts the method is forbidden.
* **Lock the final evaluation.** Validation data selects ideas; the held-out evaluation set and the
  Phase 7 confirmatory seeds are touched only under the frozen protocol.
* **Fairness.** Every competitor gets the same data, tokens, model, schedule family, tuning budget,
  hardware and its best known implementation. A win obtained by under-tuning or slowing a competitor
  is not a win.
* **Evidence-bounded claims.** Use the evidence ladder of `theory/gimbal_theory.md` for theory and
  the claim–evidence matrix (`research/ledger/claims.md`) for empirical statements.
* **Provenance.** Every reported number links to a command, config, seed, commit and raw output
  under `experiments/` or `runs/`. Tables and figures are regenerated by scripts, never typed.
* **Commit and push** after each passed gate and at least every working session:
  `git push -u origin <branch>`. Commit messages say what changed and why.

## 3. Phase lifecycle

```
pending ──► in_progress ──► passed
                 │  ▲
                 ▼  │ (repair loop, Section 4)
               failed ──► blocked (escalate, Section 9)

any state ──► stale   (an upstream artifact changed, Section 5)
stale ──► in_progress (after the phase file is rewritten)
```

`phases/STATUS.md` holds one row per phase: state, date, commit, gate evidence, open failures.
A phase is `passed` only when every exit-gate item is satisfied by recorded evidence.

## 4. The self-correcting loop

Run this loop whenever a gate item fails, a test fails, a proof does not go through, a run diverges,
or a result contradicts a prediction.

1. **Observe.** Record the exact failure: command, output, run ID, commit, and what was predicted.
2. **Classify** the failure before touching anything (ledger: `research/ledger/failures.md`):
   implementation bug · evaluator/metric defect · baseline discrepancy · proxy-fidelity failure ·
   numerical instability · optimization failure · mechanism prediction falsified · effect smaller
   than noise · resource infeasibility · false or overstrong theorem · formalization mismatch ·
   novelty overlap discovered. "Didn't work" is not a class.
3. **Localize.** Make the smallest reproduction: a unit test, a 2×2 counterexample, a toy problem,
   a single step on saved gradients. Most failures end here as bugs.
4. **Research** when the cause is not a bug. Search the internet and primary literature for the
   failure signature, read the closest papers, and use the `theory-research` attack protocol on the
   mathematics: try to break the statement (small cases, boundary values, removing each assumption),
   look for the missing hypothesis, and check whether a weaker or different statement is true.
5. **Generate at least two structurally different repairs**, e.g. change an assumption, change the
   estimator, change the update rule, change the step-size control, or change the claim. Write each
   as a hypothesis card (`research/hypotheses/`) with a unique prediction and a kill criterion.
6. **Choose by information gain**, not by appeal: run the cheapest experiment that separates the
   repairs (Monte Carlo, toy model, Lean attempt on a special case).
7. **Revise** the mathematics, theory and code together. A change to an update rule is a change to
   the theory and to its Lean statements, not just to the code.
8. **Re-verify**: Lean builds without `sorry`; unit tests pass; the Monte Carlo suite re-runs.
9. **Re-run the gate** with fresh seeds where the gate is statistical (no re-use of the seeds that
   motivated the repair).
10. **Record** the outcome in the failure ledger and decision log (`research/ledger/decisions.md`),
    then apply Section 5 if anything upstream changed.

Iteration limits: if three consecutive repair cycles on the same gate item fail, step back one level
(revise the hypothesis portfolio or the claim) instead of trying a fourth variant of the same idea.
If a whole phase has gone through eight repair cycles without progress on any gate item, escalate
(Section 9) with the failure ledger summarized.

## 5. Adaptive dependency management

Artifacts and the phases that consume them:

```
theory/gimbal_theory.md ──┬─► formal/ (Lean)                [Phase 1]
                          ├─► experiments/phase2/           [Phase 2]
                          ├─► src/gimbal/ (reference code)  [Phases 2–3]
                          └─► paper/                        [Phase 9]
src/gimbal/ ─► jax/TPU implementation [3–4] ─► pipeline [5] ─► tuning [6] ─► runs [7] ─► analysis [8]
research/ledger/claims.md ─► paper [9] ─► release [10]
```

The authoritative map is `phases/dependencies.md`: each theory item (Proposition, Theorem, Algorithm
line, hyperparameter default) is listed with every phase section, Lean file, script and paper section
that uses it.

When something changes:

1. **Diff the change** at the level of theory items: which definitions, update-rule lines, theorems,
   defaults or claims changed.
2. **Compute the affected set** from `phases/dependencies.md` (transitively).
3. **Mark stale**: set every affected phase to `stale` in `STATUS.md`; label affected results in the
   claims matrix as `invalidated by <change-id>`.
4. **Rewrite the stale phase files** so their tasks, defaults and gates match the new mathematics.
   Rewriting is mandatory even if the change looks small: a later agent will follow the file
   literally.
5. **Update the theory paper** (`theory/gimbal_theory.md`): revise statements and proofs, move old
   statements to the changelog with the reason, update Lean cross-references, and keep the evidence
   labels honest (a revised theorem drops to its lowest supported label until re-verified).
6. **Re-execute** stale phases in topological order. Results computed under an invalidated
   assumption are either recomputed or kept only as labelled historical evidence.
7. **Record** the change in `research/ledger/decisions.md` with: change-id, reason (link to failure
   entry), affected set, rewritten files, re-verification evidence.

A phase may also rewrite *itself* or later phases when it learns something that makes them wrong
(e.g. Phase 4 discovers a TPU op is unusable). The same seven steps apply.

## 6. Gates and statistics

* Gates are written before the work starts (in each phase file). Moving a gate after seeing data is
  allowed only through Section 5, with the reason recorded; the old gate and its outcome stay visible.
* Statistical gates name the experimental unit (a training run, a problem instance), the paired
  design, the test or interval, and the decision rule. Multiple comparisons across competitors use
  Holm correction. Report effect sizes with intervals, never only p-values.
* Wall-clock gates use steady-state step time (after compilation and warm-up), the median over a
  fixed window, on the same hardware and software, with every optimizer's best implementation.

## 9. Escalation (stop and ask the human)

* Hardware, quota, billing or credential problems the agent cannot fix.
* Any action that is outward-facing or hard to reverse and not already authorized in a phase file
  (changing repository visibility, deleting branches or data, publishing, spending money).
* The eight-cycle limit of Section 4 is reached.
* Evidence that the central claim is false after the protocol was followed (a negative result is a
  valid outcome; report it with the evidence rather than searching for a configuration that flips it).
